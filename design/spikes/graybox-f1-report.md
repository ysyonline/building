## 3. A* 实现要点与性能数据

**实现要点**（spike 版，刻意保持简单）：
- 开放列表线性扫描（未用二叉堆——数百节点图不值得）；节点键 `"x,z,h"` 字符串；陈旧堆项跳过
- 启发函数：曼哈顿 + 层差 × **1.4**（= 最便宜跨层边成本，保证可采纳，路径最优性有测试护栏）
- 边成本起点值：平地 1.0 / 垛口 1.5（翻越惩罚）/ 坡道边 1.4 / 云梯边 1.8（爬升慢，未来挂 hp 消耗）

**性能**（Node 20.19 / Windows，87 节点有向图）：

| 指标 | 数值 |
|---|---|
| 单次求解平均 | **0.037 ms** |
| 单次求解最差 | **1.16 ms**（2000 次含 GC 抖动） |
| 平均展开节点 | 45.0（全图 87 的 52%，跨层搜索自然扩散） |
| 全部跨层起终点 ×2000 | 失败 0 |

**容量结论**：即使按最差 1.2ms/次计，一个 40 单位的匈奴波次全量寻路 < 50ms，回合制下完全无感；**单回合全图重算（如流场）都负担得起，A* 逐单位方案成立，无需 flow field 优化**。

## 4. 踩坑记录（重要，均为真实踩中）

1. **列主序数组是模型陷阱（最重要）**：初版按「每格 (x,z) 存单值高度标签」建模，墙体写入 `h=1` 时**把同列的地面格覆盖掉了**——走廊地面在墙段整段断裂，寻路不可达（A* 展开 6 节点即枯竭）。正确结构是**层主序 `layers[h][x][z]`**：同一列同时持有地面格与墙顶格，各层是独立 2D 图、仅在连接器处并边。**F1 GDD 数据节必须显式写明层主序，禁用列主序单值高度。**
2. **three.js r160 起不再发布 UMD 构建**：`three.min.js` 已从 r160 移除，本 spike 改用 **r158**（最后的官方 UMD 全量版，控制台有一条 r150+ 弃用 console.warn，无害）。项目正式选型时注意：r160+ 需走 ES Modules 或打包器。
3. **UMD 禁止包 IIFE**：构建时误把 UMD 库体包进 `(function(){...})()` 再赋值给 `window.THREE`——UMD 依赖 globalThis 副作用挂载，包装导致赋值表达式把挂载结果**覆盖为 undefined**。已改为库体原样内联零包装。
4. **坡道连接器必须跨相邻列**：若 a/b 取同列上下格，坡道斜体埋进墙体不可见；跨列相邻格 + 斜板 `lookAt` 高端建模，视觉与图论一致。
5. **无头测试环境 UMD 走错分支**：Node 直接 eval 时 `typeof exports === 'object'` 使 UMD 走 CommonJS 分支填充 exports 而不挂 `window.THREE`——**浏览器无此变量不受影响**；无头冒烟必须用 vm 裸上下文（无 exports/module/define）。

## 5. 对 F1 GDD 的技术输入清单

1. **数据结构（必采）**：`layers[h][x][z] → 类型|null`，h∈{0,1,2}，类型 `{ground|wall|walk|merlon|tower}`；主键 `(x,z,h)`。禁止列主序单值高度（坑 1）。
2. **连接器字段建议**：`{ id, kind:'ramp'|'ladder', a:{x,z,h}, b:{x,z,h}, open:bool, hp?:int }`；预留位（spike 未消费，GDD 裁定）：单向性、通行容量、破坏阈值、跨层通行时消耗。边成本起点：坡道 1.4 / 云梯 1.8 / 垛口 1.5。
3. **占位容量（R1 残余风险初裁）**：MVP 定值**每格 2**。满格入队失败 → 建议策略「等待或重寻路」，由 C1 GDD 裁定；渲染侧 2 单位/格无遮挡问题（错位摆放即可）。
4. **切层渲染实现路径**：每层一个 InstancedMesh，切层=整层材质 transparent/opacity 切换（O(1)/次）；相机档位与聚焦层联动。美术（林绘澄）可在此底子上提分层着色/描边需求。
5. **走廊规模背书**：20×3 走廊 = 87 节点，处于建议规模上限；在此规模上「3 关节奏差异用墙段长度 + 连接器数量 + 波次构成做区分」（§5.4 R4 建议）数据量完全可控。
6. **未决规则移交 C1**：多连接器共用落点格（如 L2 与墙顶格共存）目前允许，MVP 够用；同格多连接器的占用/容量细则 C1 GDD 定。

## 6. R2 残余风险初步评估（床弩「穿透一列」射线判定代价）

无头实测（87 盒体场景，`tools/r2-bench.js`）：

| 方案 | 单发代价 | 说明 |
|---|---|---|
| A 网格步进（同层轴向逐格查占位） | **0.28 μs/发** | 纯数组操作，天然精确落在网格语义上 |
| B 真射线（Raycaster ×3 射线 vs 87 盒） | **115 μs/发** | ≈ A 的 400 倍 |

**初步裁定建议**：
- 10 床弩齐射场景下，A 方案开销可忽略（<3μs）；B 方案也只有 ~1.2ms，**两者性能都成立，这不是瓶颈项**。
- 真正的裁决点是**玩法语义**而非性能：建议 P2 支柱「穿透一列」优先定义为**同层轴向列 + 网格步进**（沿墙顶马道打，命中判定=列上逐格占位查询），可读性与确定性更好；跨层斜向穿透若想要，真射线代价可接受，但需做场景过滤（跳过单位网格/地面层），且把「列」的命中表现一致性交给美术评审。
- 本测试为纯数学无头环境，浏览器内 WebGL 渲染管线下的 raycast 需复测（页面内已留「R2 射线压测」按钮），预期同数量级。

## 8. 对视觉对齐备忘（GW-P2-ART-F1）的接口

- 切层半透明参数起点：`opacity 0.14 + depthWrite:false`，灰盒下可读性成立；可在此基础上议分层色相/轮廓化。
- 地形渲染 3 draw call + 连接器/单位独立 mesh，网格贴花（格子线）可直接加在层 InstancedMesh 上，代价低。
