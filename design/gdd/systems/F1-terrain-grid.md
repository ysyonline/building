## 1. 概述

### 1.1 职责定义

F1 定义多层立体棋盘的**纯数据模型与结构契约**：坐标系、格子分类、占位容量、跨层连接器（静态坡道 + 动态云梯）、走廊式关卡数据结构，以及向下游系统（C1/C2/C5/C8/P1/P2/P3）提供的只读查询接口。F1 是**结构宿主**而非行为宿主：路径计算、单位行为、结算公式、渲染实现均为下游系统的职责，F1 只保证「问得出来、答得一致」。

一句话：**把「一段长城」变成一张可查询、可修改、可存档的分层有向图。**

### 1.2 设计目标与支柱挂钩

| 支柱/定稿项 | F1 落点 |
|---|---|
| P2「高度即力量」 | 高度标签 h 是格子的一等属性；高度差查询 O(1)，供 C5 结算修正（数值归 C5） |
| P3「每段城墙都有故事」 | 格子类型带名称与文案锚点（垛口/马道/烽燧顶），教学关按格讲地形 |
| 决策①缓解：走廊式关卡 | §9 数据结构以「走廊段落 + 端点烽燧」为骨架，杜绝自由地形 |
| §5 MVS 四条件 | 本 GDD 覆盖条件 1（走廊）、2（分层网格+显式连接器）、3（云梯=动态连接器数据模型；正式采纳在 C1）、4（固定档位相机挂 §6.3） |

### 1.3 非目标（Non-goals）

- ❌ 任意 3D/体素地形、非正交网格、曲面地形——不允许进入 MVP。
- ❌ 寻路算法（A*/flow field 选型、动态重规划策略）→ C1。
- ❌ 移动消耗的**数值基准**→ F3 表 + C1 GDD（本文只定义表结构与查询接口）。
- ❌ 单位属性/行为 → C2；设施建造校验 → C7；高度修正系数 → C5。
- ❌ 视觉表现、遮挡渲染 → P1/P2（本文只交付层级结构）。

### 1.4 关键裁定速览（TL;DR）

| # | 裁定 | 一句话 |
|---|---|---|
| A | 坐标系 | 走廊局部坐标 (x,z)，x 沿城墙轴向 0..W-1，z 纵深 0..2，x 单调对应离烽燧距离；世界坐标换算经单点适配器，核心层不感知 Three.js |
| B | 高度 | h∈{0 地面, 1 墙顶/马道, 2 烽燧顶}，符号常量枚举，禁魔法数字 |
| C | 格子类型 | 7 类：WALL（结构体）/ PARAPET / RAMPART_WALK / GATE（门洞）/ SLOPE / GROUND / BEACON_FLOOR；无「洞/坑」类，垂直地形差只允许出现在连接器与墙结构处 |
| D | **占位容量（R1 结论）** | 按格类型分容量：垛口 1 单位、马道 2、地面 4、门洞 1、烽燧顶 1、坡道 1、墙结构 0；垛口=1×1 独占位；**堆叠上限 4**；设施全部独占；容量数值全部 F3 表宿主可调 |
| E | 连接器 | 8 字段统一数据结构（id/from/to/connKind/orient/occupancy/status/lifetime）；SLOPE+LADDER 共用；LADDER 承载与顶端占用分离（§4.4） |
| F | 存取模型 | 只读查询接口供下游；写操作收敛为 6 个显式 mutation（§3.8），全部带合法性校验、发事件、可序列化——这是存档（F5）与模拟器（X5）的地基 |
| G | 查询预算 | 状态/邻接/高度差/容量查询 O(1)；全图快照 O(N)（N≈200-400）供 AI 评估；图变更时脏标记增量重建邻接 |
| H | 关卡校验 | 17 条加载期校验规则（§8.4）+ 三关最小结构判据（§10.4）；不可达=硬错误拒绝加载 |

## 2. 机制

### 2.1 分层 2D 网格（2.5D heightmap grid）

- 走廊为**单段**轴向网格：`x ∈ [0, W-1]`（沿城墙延伸方向），`z ∈ [0, 2]`（走廊纵深），每格带高度标签 h。
- 水平四邻接（N/S/E/W）；**同层水平移动永远不可能改变 h**——高度变化只发生在连接器（§2.4），这是全系统最重要的不变量，寻路/容量/结算全部依赖它。
- 跨层不存在隐式边：任何垂直位移必须经过显式连接器对象。

```
剖面示意（z=0 侧为匈奴来向，z=2 侧为守军内侧）：

 h=2                    ┌──────┐
                        │烽燧顶│ (BEACON_FLOOR)
 h=1      ═════════════╣垛│马道│垛╠═════════════
           WALL 结构体   │  │(RAMPART_WALK)│  ← SLOPE 在马道端点落地
 h=0    ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓
         GROUND（匈奴集结/冲锋/冲车道）      [GATE 门洞]
```

### 2.2 高度层

| h | 名称 | 定位 | 典型格类型 |
|---|---|---|---|
| 0 | 地面层 | 匈奴集结/冲锋/冲车道；守军出击出发点 | GROUND、GATE |
| 1 | 墙顶层 | 守军主防线：垛口堵击、床弩架设、滚木礌石投放 | PARAPET、RAMPART_WALK、SLOPE |
| 2 | 烽燧顶 | 帅帐/视野制高点（C12 Alpha 挂点，MVP 仅帅帐所在与胜负判定载体） | BEACON_FLOOR |

- 规则：**h=2 只允许经烽燧内部 SLOPE（h0→h2 一步）到达**，MVP 烽燧顶不直接对外墙开放，避免出现跨层裁决歧义。
- 高度标签是**类型推导的一部分**：格类型与其承载高度一一绑定（§3.1 校验），不存在「h=0 的垛口」。

### 2.3 格子类型（最终集合：7 类，MVP 全用，枚举保留扩展位）

| 枚举 | 名称 | 容量 | 说明 |
|---|---|---|---|
| `WALL` | 墙结构体 | 0 | 墙体剖面格，**不可进入不可交互**，纯结构/渲染体。垛口与马道以外的一切墙内格 |
| `PARAPET` | 垛口 | 1 | 墙顶外侧一线战斗位，掩体属性载体（骑射手格挡逻辑归 C5，F1 只给标签） |
| `RAMPART_WALK` | 马道 | 2 | 墙顶内侧走道：器械架设位、戍卒调度线 |
| `GATE` | 门洞 | 1 | 地面层唯一**允许地面→马道通行**的格；冲车目标；被堵则走廊战立意成立 |
| `SLOPE` | 坡道 | 1 | 跨层移动格，绑定一条静态 Connector（§2.4）；同时是本层正常格 |
| `GROUND` | 地面 | 4 | 开阔地/集结区，容量最大，承载人海 |
| `BEACON_FLOOR` | 烽燧顶 | 1 | 帅帐所在；失守即触发守方败北判定之一 |

> 扩展位：`RUBBLE`（塌墙）、`TRENCH`（陷马坑）等 Alpha/Beta 候选，枚举预留但 MVP 校验器直接拒绝（§8.4-V13），防止未设计类型溜进关卡数据。
> 裁定说明：不设「洞/坑/悬空平台」类——**垂直地形差只允许出现在连接器与墙结构处**，保持「层内平坦」不变量（§2.1）。

### 2.4 连接器模型（坡道 + 云梯统一图论）

#### 2.4.1 模型定义

- **连接器 = 一条有向跨层边 + 一个实体承载器**，持久化在关卡数据（静态）或战局状态（动态）中，与格子模型平行。
- 两种实现共享同一结构：
  - `SLOPE`（坡道/梯道）：**静态**，关卡数据声明，不可摧毁，边常在；
  - `LADDER`（云梯）：**动态**，由 C2/C8 在战局中架设生成，可被摧毁，断边即失效。
- 邻接图 = {各层水平四邻接边} ∪ {全部 status=ACTIVE 的连接器边}。寻路、AI、高度查询一律走此图。

#### 2.4.2 数据结构（8 字段，引擎无关 TS）

```ts
interface Connector {
  id: string;            // 全局唯一，静态坡道建议 "sl_<关卡id>_<n>"
  from: CellRef;         // 低端格 (x,z,h=0)
  to: CellRef;           // 高端格 (x,z,h=1|2)
  connKind: 'SLOPE' | 'LADDER';
  orient: 'AXIAL' | 'FRONTAL';   // AXIAL=顺墙爬（登马道）｜FRONTAL=迎面爬（登垛口）
  occupancy: OccupancyState;     // {units: UnitId[], orderedByMovePriority} ← 独立容量模型，不占用格容量
  status: 'ACTIVE' | 'DESTROYED' | 'INACTIVE';
  lifetime: {
    createdTurn?: number;        // 动态梯：架设回合（静态坡道 undefined）
    currentHp?: number;          // 动态梯：当前耐久（静态坡道 undefined = 不可摧毁）
  };
}
```

**静态坡道落格规则**：两端格必须为 `SLOPE` 类型格；坡道格自身遵守格容量（§3.1）。

#### 2.4.3 方向语义与玩法含义

- `FRONTAL`（迎面爬）：梯顶落在 **PARAPET** → 攻方直接顶在守军垛口战斗位上，攻防矛盾最尖锐处（「云梯登城即抹平高度差」的实体）。攻方在梯上是 `EXPOSED` 暴露态（修正数值归 C5 表）。
- `AXIAL`（顺墙爬）：梯顶落在 **RAMPART_WALK** → 端点常是器械架设位，威胁床弩等设施，逼守方留预备队。
- 匈奴 AI 选点策略（倾向 FRONTAL>AXIAL、优先守军火力薄弱垛口）归 C8 GDD，F1 不约束。

#### 2.4.4 承载与摧毁语义

- **承载**：单位处于「攀梯中」时，登记在 `occupancy`（容量=1，§4.4），**同时保留逻辑位置=梯底格**——承载与格子占用分离，是「梯毁坠亡」「梯毁封锁」两条规则的数据前提。
- **摧毁**（动态梯特有）：`status: ACTIVE→DESTROYED`；邻接图断边；`occupancy` 内单位触发「坠落」处理（伤害归 C5，位移回 `from` 格由 F1 执行，见 §5-E2）；`lifetime.currentHp` 由 C5 攻击写入，F1 只持有。

### 2.5 占位与容量模型（残余风险 R1 的正式结论）

#### 2.5.1 裁定原则

1. **堵口/堵垛口成立的前提是「小容量」**：一线战斗位容量必须为 1，否则人海瞬间淹没战线，攻防张力消失（P4「侥幸守住的快感」被稀释）。
2. **容量差 = 走廊立体感的战术来源**：地面开阔容量大 → 匈奴人海在地面铺开 → 被连接器「漏斗」收束到容量 1 的攀城点 → 守军以一当十。这个「4→2→1 漏斗」是 F1 提供的最核心战术结构。
3. **渲染密度护栏**：按 §10.2 参数推演全场瞬时满承载 ≈ 78 单位，模型上限 80，Three.js InstancedMesh 无压力；若平衡期上调容量数值，渲染按「单格堆叠可视化（最多 4）」处理，不随容量线性增模（林绘澄视觉对齐备忘挂 R3）。

#### 2.5.2 容量表

| 格类型 | 容量 | 玩法含义 |
|---|---|---|
| PARAPET 垛口 | **1** | 一人当关；垛口=**1×1 独占位** |
| RAMPART_WALK 马道 | **2** | 可并立，器械占位走设施规则（下一行） |
| GATE 门洞 | **1** | 门洞互斥，堵口玩法的物理基础 |
| BEACON_FLOOR 烽燧顶 | **1** | 帅帐区不叠单位 |
| SLOPE 坡道 | **1** | 坡道单列通行 |
| GROUND 地面 | **4** | 人海铺开区 |
| WALL 墙结构体 | 0 | 不可进入 |

> **容量数值全部标注：F3 表宿主（新表 `grid-capacity.json`，键=CellKind），平衡期可调，禁止硬编码。** §2.5.2 为 MVP 初值。

#### 2.5.3 容量判定细节

- 「同格 2 单位」按「同一受击判定整体、同生共死」处理（RFC 裁定②），容量语义=「多单位可于同格**共存**」，非「多份独立靶」。伤害对同格所有单位各投一次（如 PARAPET 容量 1 则恒无此情形；GROUND 容量 4 会出现）。个体 HP 独立结算归 C5。
- **设施独立于单位容量**：设施（床弩/礌石/戍卒）使用**全部独占格**规则，建在哪个格、占哪个格、被毁后格释放——细则归 C7（建造校验）/C3（设施数据），F1 只保证占位查询接口（§3.7）返回一致答案。
- 扩展性约束（与督队裁定同源的工程纪律）：容量表外置 F3，本文代码示例中不出现字面量容量数字。

### 2.6 单位占用状态机

| 状态 | 进入 | 格容量 | 移动 | 备注 |
|---|---|---|---|---|
| `IN_CELL` | 常态 | 占 1 个槽位 | 正常 | 登记 `cellId + slotIndex` |
| `ON_CONNECTOR` | 进入坡道/云梯 | **不占格容量** | 冻结 | 逻辑位置=梯底格，登记于 `connector.occupancy`；仍可被选中被指令 |
| `OFFBOARD` | 未部署/预备队 | 0 | — | C7 建设期部署即申请转 `IN_CELL` |

申请序：容量检查 → 绑定 → 容量满则整条移动指令拒绝（部分完成的路径段回滚由 C1 执行，F1 保证申请原子性）。

### 2.7 关卡结构（走廊式骨架）

- **一段城墙 + 两端点**：地面走廊沿 x 轴延伸；一端为**烽燧**（守方核心，h=2）；另一端为开放式来敌端（h=0）。守军内侧（z=2 侧）可设窄条预备队地面带。
- 敌方主攻方向 = 沿 x 轴正向推进。多波次全从开放端进场（佯攻/主攻的**节奏**差异归 C9 波次编排，地形不提供第二轴线）。
- **规模护栏**：W(列) ∈ [12, 20]，纵深 z=3（0..2），全图格数 ≈ 200-400（与 §5.1 量级一致）。超界触发 §8.4-V14 警告。
- 三关差异化用**三变量**（墙段长度/连接器数量/波次构成），不新增地形类型（§10，R4 落点）。

## 3. 数据

> 本节为引擎无关数据契约。运行形态建议：**静态层 immutable + 动态层 mutable**；MVP 可用简单可变对象+校验，结构不变（「待与 spike 对齐」条目 §11-1）。

### 3.1 Cell（格子）

```ts
interface Cell {
  id: CellId;                 // `${x}_${z}`，层内局部坐标即 ID
  x: number; z: number;       // 走廊局部坐标
  h: 0 | 1 | 2;               // 高度标签（枚举 Height）
  kind: CellKind;             // §2.3 七类之一
  passable: boolean;          // 可通行位：kind !== 'WALL'
  occupantIds: UnitId[];      // 当前占用槽位（≤ capacity(kind)，有序）
  facilityId?: FacilityId;    // 设施独占占位（C3/C7 写入）
  meta?: CellMeta;            // {name?: 文案锚点（P3 支柱）, texture?: 美术标签（挂 R3，林绘澄，可空）}
}
```

`passable` 判定 = `kind !== 'WALL'`；进入合法还须通过容量检查——「可通行」与「可进入」分离（满格可通行但不可进入）。

### 3.2 走廊关卡静态数据（LevelMap）

```ts
interface LevelMap {
  version: 1;                              // 结构版本号，跨存档兼容用
  levelId: string;                         // "MVP_L1" | "MVP_L2" | "MVP_L3"
  width: number;                           // 走廊列数 W ∈ [12,20]
  depth: 3;                                // MVP 恒 3（z=0..2）；留字段防硬编码
  cells: Cell[];                           // 由 §9.1 生成器生成
  connectors: Connector[];                 // 静态坡道（LADDER 不在此，运行期生成）
  beacon: BeaconDef;                       // 烽燧：{cellId(必然 h=2), durability, ...}
  deployZones: DeployZone[];               // 部署区（C7 消费）
  enemySpawns: EnemySpawnDef[];            // 敌方出生端配置（C9 消费）
  terrainRules: TerrainRules;              // §4.5 参数包（F3 表挂载点，本身不含数值基准）
}
```

`TerrainRules`：**C1 移动消耗、C5 修正、C8 评分的地形参数挂载点**——F1 定义「参数包里有什么键」，数值基准归 F3 表与各消费方 GDD（§4.5）。

### 3.3 战局动态地形状态（TerrainRuntime，F5 存档的 F1 部分）

```ts
interface TerrainRuntime {
  levelId: string;
  dynamicConnectors: Connector[];          // LADDER 运行时列表（架设增/被毁改 status）
  cellOccupancy: Record<CellId, {units: UnitId[]; facility?: FacilityId}>;
  turn: number;                            // 变更记账用
}
```

### 3.4 层内邻接（静态，可预计算）

```ts
interface Adjacency {
  neighbors: Record<CellId, CellId[]>;     // 水平四邻，passable 过滤
  connectorsFrom: Record<CellId, ConnectorId[]>;  // 该格为 from/to 的 ACTIVE 连接器
}
```

### 3.5 枚举与命名一致性

`Height{0,1,2}`、`CellKind`（7 值）、`ConnectorKind{'SLOPE','LADDER'}`、`Orient{'AXIAL','FRONTAL'}`、`ConnStatus{'ACTIVE','DESTROYED','INACTIVE'}`、`UnitPlacement{'IN_CELL','ON_CONNECTOR','OFFBOARD'}`（§2.6）。枚举命名与 `systems-breakdown.md` §5.2 表中「墙/垛口/马道/坡道/地面/门洞」一一对应（GATE=门洞，WALL=墙结构体，BEACON_FLOOR 为本文新增第 7 类）。

### 3.6 与下游系统的数据契约（谁写谁读）

| 字段 | 写入方 | 读取方 |
|---|---|---|
| `occupantIds` / `facilityId` | C7（部署/建造）、C1（移动落格）、C2（增删单位） | 全部 |
| `connector.status` / `lifetime.currentHp` | C2/C8（架设）、C5（耐久伤害） | C1/C8/P1 |
| `connector.occupancy` | C1（进入/离开/坠梯） | C5（梯上单位受击）、P1（攀爬表现） |
| `passable` / `Adjacency` | 仅 F1 内部（构造/变更） | C1 寻路、C8 AI、C5 射线 |

### 3.7 对外只读查询接口（TerrainQuery，供 §6.2 契约）

```ts
interface TerrainQuery {
  getCell(id: CellId): Readonly<Cell>;
  getCellAt(x: number, z: number): Readonly<Cell>;
  heightDiff(a: CellId, b: CellId): -2 | -1 | 0 | 1 | 2;   // b.h − a.h，供 C5
  getAdjacency(id: CellId): Readonly<{orth: CellId[]; via: ConnectorRef[]}>;
  getConnector(id: ConnectorId): Readonly<Connector>;
  getActiveConnectors(kind?: ConnectorKind): Readonly<Connector[]>;
  occupancyOf(id: CellId): {units: Readonly<UnitId[]>; capacity: number};
  canPlace(id: CellId, n: number): boolean;   // 容量检查（不含设施校验，归 C7）
  snapshot(): LevelMapReadView;               // O(N) 全图只读视图，供 C8 评分/X5 模拟
}
```

预算：单点查询 O(1)；`snapshot()` O(N)，N ≤ 400，每回合调用频次约束「每阵营每回合 ≤ 2 次」。

### 3.8 F1 的写操作白名单（全部带校验 + 事件 + 可序列化）

`placeUnit / removeUnit / moveUnit(原子跨格) / registerFacility / addConnector(架梯) / destroyConnector(梯毁)`。
跨格移动为原子操作：先目标格校验（passable+容量）再双端登记，失败则整条拒绝、原格不动；不存在半更新状态。所有 mutation 发事件（供 P1 渲染订阅/P4 告警/X5 录制），事件流可重放=存档一致性地基（配合 F4 确定性随机）。

## 4. 公式

> 统一格式：编号 ｜ 名称 ｜ 变量与单位 ｜ 表达式 ｜ 消费方。凡数值基准一律标「F3 表宿主」。

### 4.1 格 ID 与坐标

- `F1.1 ｜ CellId = \`${x}_${z}\`（层内局部坐标）`
- 世界尺度：**1 格 = 4 米**（MVP 定值；定值本身非平衡变量，但走 F3 常量表、禁硬编码）。视觉对齐备忘 §4.1 贴花密度按此假设，无需回传复核。
  - **格尺寸初值建议（回应视觉备忘 Q6）**：1 格 = 4 世界单位（与林绘澄贴花密度假设一致）；此值属渲染常量，正式定值在 spike 相机标定（Q1）后由 P1/P2 GDD 收口，若偏离 4m 需回传美术复核 §4.1 贴花密度。

### 4.2 邻接

- `F1.3 ｜ 水平邻域（含自）：N(x,z) = {(x+dx, z+dz) | (dx,dz) ∈ {(±1,0),(0,±1),(0,0)}, 界内}`
- `F1.4 ｜ 层内移动边：(a→b) ⇔ b ∈ N(a) ∧ b.passable ∧ 等高`

### 4.3 跨层边（连接器生效判定）

- `F1.5 ｜ 跨层边生效：(c: Connector) 有效 ⇔ c.status = ACTIVE`
- `F1.6 ｜ 跨层邻接：via(c, from) = c.to if (c.status=ACTIVE ∧ c.from=from)；反向同理`

### 4.4 容量与承载

- `F1.7 ｜ 格容量：cap(cell) = CapacityTable[cell.kind] ｜ 容量键=CellKind，表宿主 F3（grid-capacity.json），初值见 §2.5.2`
- `F1.8 ｜ 格容量判定：canPlace(cell, n) ⇔ cell.passable ∧ |cell.occupantIds| + n ≤ cap(cell) ｜ n∈ℕ`
- `F1.9 ｜ 连接器承载容量：capOcc(c) = 1 ｜ 单位同时攀爬数=1（表宿主 F3，同 grid-capacity.json，键=LADDER/SLOPE）`
- `F1.10 ｜ 承载判定：canBoard(c) ⇔ c.status=ACTIVE ∧ |c.occupancy.units| < capOcc(c)`
- `F1.11 ｜ 梯顶封顶（先到先得）：登顶出梯允许 ⇔ canPlace(c.to, 1)；不允许则攀爬单位留在 occupancy 排队`
  - 玩法含义：顶部 PARAPET 被垛口戍卒占满时，梯上单位无法登顶——「**垛口堵击**」的物理实现；堵点即玩法（P2 支柱「占位先于火力」）。
- `F1.12 ｜ 堆叠上限：|occupantIds| ≤ min(cap(cell), StackLimit) ｜ StackLimit=4（表宿主 F3），护栏防数值调参溢出渲染预算`

### 4.5 地形参数包（TerrainRules 键清单，数值归 F3/各消费方）

| 键 | 含义 | 初值 | 宿主 |
|---|---|---|---|
| `moveCost plains` | 地面平移消耗 | 1 | F3+C1 |
| `moveCost climb` | 连接器攀爬段消耗 | 2 | F3+C1 |
| `moveCost gate` | 门洞格消耗 | 2 | F3+C1 |
| `exposedMod ladder` | 梯上暴露态修正 | 见 C5 表 | F3+C5 |
| `ladderHp` | 云梯耐久 | 待 C2/C5 GDD 裁定 | F3 |
| `stackLimit` | 堆叠上限 | 4 | F3 |

### 4.6 不变量（全部可单测，验收判据直接引用）

- INV1：格容量恒不超——`∀cell: |occupantIds| + (facility?1:0) ≤ cap(cell)`（设施占位独立于单位容量的校验合流点见 §3.6）。
- INV2：连接器 occupancy ≤ 1；`ON_CONNECTOR` 单位逻辑位置 = `c.from`。
- INV3：容器内被引用的每个 CellId/UnitId/ConnectorId 均存在且唯一。
- INV4：跨格移动原子性——不存在「离开 A 未进 B」中间态。
- INV5：无「洞」——垂直层差只经 Connector；任意格存在到烽燧格的路径（连通性）。
- INV6：动态梯摧毁原子性——断边与 occupancy 清空同一事务内完成。

## 5. 边缘情况

> 裁定者=本文；跨系统伤害数值一律转 C5。格式：编号｜场景｜裁定｜消费方。

### A. 云梯与连接器

- **E1｜架梯时梯底格已满**：LADDER `from` 固定为匈奴推进方向邻接的 GROUND 格，架设动作本身不要求该格有空槽；梯底单位占 GROUND 正常槽位。若敌我单位占满且后续无单位可从该格登梯——梯位选址逻辑归 C8（AI 会倾向选空旷段）。**待澄清归 C8**：AI 选址约束清单是否需要 F1 提供专用查询。
- **E2｜梯被毁时梯上单位**（任务指定必答）：`occupancy` 单位触发坠落——位移回 `from` 格（若 from 满，顺延该层邻接最近空格，找不到则 OFFBOARD→下回合部署复位）；伤害数值归 C5 表。若 from 侧已无任何可落格（被围死）允许 OFFBOARD 兜底，**不允许悬空引用**（INV2/INV6）。
- **E3｜梯顶格单位在攀爬者登顶前离开/被击杀**：出梯判定 `canPlace` 实时评估（F1.11），顶格空出即可登；无「锁顶」状态。
- **E4｜同一地面格发起两条云梯**（双梯并立）：允许——LADDER 是独立实体、承载独立于格容量；两梯顶可分别对准不同垛口，形成「一点双梯」强攻。渲染密度护栏见 §2.5.1。
- **E5｜被毁梯的残留（裁定视觉对齐备忘 Q2）**：残骸**不占格**——`status=DESTROYED` 后该边即从邻接图摘除、`occupancy` 已清空（INV6），地面格容量不受影响；`DESTROYED` 记录保留至本回合结束供 P1 演出（残骸躺平＝纯视觉标记，与视觉备忘 §3「仅作标记不占格」建议一致），下一补给相位清除出 `dynamicConnectors`；清除动作同样发事件（P1 清理模型）。
- **E6｜静态坡道不可摧毁**：`lifetime` 字段 undefined 即不可摧毁；C5 对其攻击结算直接无效（no-op）。校验保证 SLOPE 类 Connector 恒 ACTIVE（§8.4-V9）。

### B. 单位与格子互斥

- **E7｜单位站在被摧毁设施格**（任务指定）：设施被毁→C3 释放 `facilityId`→格子恢复纯格语义；正站在同格的单位（马道与器械可共存场景）**不受影响、不位移**。设施「占格但非排他」情形的合法性由 C7 建造校验裁定，F1 只保证释放动作后 occupancy 一致（INV1/INV3）。
- **E8｜满格拒绝与路径回滚**：移动指令遇中途格被第三方抢占（先手结算优先）→ C1 回滚该单位本轮剩余路径，F1 保证已完成的段次不产生脏状态（原子申请）。
- **E9｜推挤/换位**：MVP **不支持**主动换位、推挤。堵死就是堵死——这是「占位先于火力」的推论；Alpha 若引入 swap，需扩写 F1.8 为双向原子操作。
- **E10｜h=2 烽燧顶唯一性**：全图仅 1 个 BEACON_FLOOR（校验 V4），杜绝「双帅帐」歧义；失守判定归 X1，F1 只提供烽燧格坐标。

### C. 通行与结构

- **E11｜门洞通行规则**（任务指定）：GATE 是 h=0 层唯一「地面→马道」连接点，作为一条特殊静态 Connector（SLOPE 类，orient=FRONTAL）建模——复用统一连接器模型，避免特殊分支。GATE 格自身容量 1：单列通行，冲车（大体型，占位细则归 C2）被拒于门外是「堵门」玩法的物理基础。GATE 被 C3「封门」后由该系统写 Connector INACTIVE（F1 提供接口，封门数值归 C3/C6）。
  - **坡道通行权（回应视觉备忘 Q4，本文裁定）**：静态坡道/GATE 默认**双方共用**（敌我可通行，攻方限步兵：骑射手受限、冲车限 L0；视觉「双条边」编码），这是走廊战的张力来源——守军预备队经坡道驰援马道的同时，匈奴破门后同样可循坡道登墙，通行权本身即攻防争夺对象。L1↔L2 烽燧梯为**守方专属**（单条实边编码），防匈奴上墙后直捣帅帐。MVP 不做可摧毁坡道；若 Alpha 引入专属通行/可摧毁坡道，扩 orient 枚举或加 factionLock 字段（F3 表），不动连接器主体结构。视觉侧按三级视觉码编码（备忘 v1.1：双条实边=共用坡道/单条实边=守方专属烽燧梯/单条虚线=可切断云梯），无需单条边方案。
  - **坡头格战术热点（美术侧提示，采纳进 §6.1）**：坡道顶格（坡头）是守方堵口热点位——P3/P4 的威胁范围与可部署提示 decal 中坡头格优先级最高；F1 提供 `pickCandidates`/邻接查询即可支撑，无需新增 API。
- **E12｜冲车对 GATE/墙体**：冲车不进格，作为「攻击墙体结构的器械实体」处理——是否占用地面格归 C2 裁定（F1 不预支结论）；F1 提供墙体结构查询（命中判定用）。
- **E13｜多波次同时登城**：两梯+坡道三点并行承压时，`occupancy` 天然串行化（各梯容量 1），不需要全局锁；攀爬排序（谁先登）归 C1 移动结算次序。

### D. 交互与渲染消歧

- **E14｜多层同屏点击消歧**（任务指定）：点击射线按「当前相机档位所在层优先」消歧——地面档优先命中 h=0/1 中的高可交互格，墙顶档优先 h=1/2；同投影多候选时取**离相机近者**并列出备选列表供第二次点击（备选列表承载归 P3）。F1 提供 `pickCandidates(worldRay) → CellId[]`（按层排序）查询。
- **E15｜切层渲染时的逻辑一致性**：半透明上层**逻辑上仍然存在且可被点击**（规则：半透明≠不可交互）；P1 表现由视觉对齐备忘（R3）约束，F1 不提供「逻辑隐藏」API，防止表现与逻辑脱钩。
  - **半透明层下单位可读性（回应视觉备忘 Q5，F1 侧口径）**：林绘澄「半透明层内单位 ×0.5 透明」方案与 E15 兼容——表现层透明不影响 F1 拾取（`pickCandidates` 按 CellId 寻址，不感知 opacity）；但该层单位的**可选中性需保留**，P3 实现时禁用 opacity 做点击过滤。此口径待 C10 托管微操 GDD 复核操作场景后正式关闭。
- **E16｜存档/读档穿越梯状态**：`TerrainRuntime` 全量序列化（含 DESTROYED 残留）；读档后邻接图按快照重建，不走增量重放（MVP 简化；X5 对拍时用事件流重放校验一致性，归 X5）。

## 9. 走廊式关卡数据结构（交付物正文）

### 9.1 关卡 JSON 结构草案（LevelMap v1）

```jsonc
{
  "version": 1,
  "levelId": "MVP_L1",
  "width": 14,                     // 墙段长度：三变量之一
  "depth": 3,
  "terrainRulesRef": "terrain-rules.json",
  "capacityTableRef": "grid-capacity.json",
  "connectors": [                  // 静态坡道 + GATE 特殊连接器；云梯不在此
    { "id": "sl_L1_1", "connKind": "SLOPE", "orient": "AXIAL",
      "from": "2_0_h0", "to": "2_0_h1" },
    { "id": "sl_L1_2", "connKind": "SLOPE", "orient": "FRONTAL",
      "from": "12_1_h0", "to": "12_1_h1" },
    { "id": "sl_L1_gate", "connKind": "SLOPE", "orient": "FRONTAL",
      "from": "7_0_h0", "to": "7_0_h1", "tag": "GATE" }
  ],
  "beacon": { "cellId": "13_1_h2", "durabilityRef": "beacon.json" },
  "deployZones": [
    { "id": "dz_wall", "cells": ["6_1_h1", "7_1_h1", "8_1_h1"], "budgetRef": "l1-economy.json" },
    { "id": "dz_reserve", "cells": ["4_2_h0", "5_2_h0", "6_2_h0"] }
  ],
  "enemySpawns": [
    { "id": "spawn_main", "edge": "x_low", "zRange": [0, 2], "waveRef": "l1-waves.json" }
  ],
  "meta": { "title": "第一夜·初雪", "teachingMode": true }
}
```

坐标记法说明：单元格数据内仍为 `(x,z,h)` 三元组（§3.1），JSON 中 `*_h{n}` 为可读简记。

### 9.2 单墙段三高度生成规则（代码级，从 W 与连接器声明推导 cells）

```
∀x ∈ [0, W):  GROUND(x, 0, h=0)；GROUND(x, 1, h=0)；GROUND(x, 2, h=0)
墙体结构列（连接器 x 除外）：WALL(x, 0, h=1)，WALL(x, 2, h=1)
每个静态连接器 x 位置：
  PARAPET(x, 0, h=1) —— 外线垛口（若 orient=FRONTAL 落点）
  RAMPART_WALK(x, 1, h=1) —— 内线马道
  SLOPE(x, *, h) —— 连接器占位格（容量 1）
烽燧列 x_b：BEACON_FLOOR(x_b, 1, h=2) + 内部 SLOPE 连接器（h0→h2）
守军侧预备带：GROUND(x, 2, h=0) 保持可部署（deployZones 消费）
```

- z=0 为外侧（匈奴主攻面），z=2 为内侧（守军预备面）；马道 z=1 居中可横向调度。
- 该生成器保证 V6 边界规则与「无洞不变量」INV5 结构性成立。

### 9.3 与波次/经济配置的边界

`LevelMap` 不含波次构成与经济数值——只持 `waveRef / budgetRef` 引用（归 C9/C6 表）。三关差异 = width、connectors 数量与落位、waveRef 内容三变量（§10），**地形类型集合恒定**。
