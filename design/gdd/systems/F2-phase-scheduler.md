## 1. 概述

### 1.1 职责定义

F2 是战局的**时钟与秩序**：持有回合计数与相位状态机，裁定四相位（建设→敌军→攻防结算→补给）的合法迁移、相位内的结算顺序、攻防结算相位的速度序行动循环，以及胜负判定的检查点时点。F2 不做任何游戏内容判断——它只保证「谁在何时被允许做什么、事件按什么顺序发生、何时裁决胜负」。

一句话：**把「一夜攻防」切成一段所有系统都认的、确定的时间轴。**

### 1.2 设计目标与支柱挂钩

| 支柱/定稿项 | F2 落点 |
|---|---|
| P4「侥幸守住的快感」 | 胜负判定收敛到**固定检查点**（D 相位），烽燧被破=立即中止 C 相位剩余行动序——「最后一轮的极限调度」有明确的截止线，紧张感有节奏而非悬置 |
| 决策⑤ 建设不限时 | A 相位无任何墙钟依赖：状态机纯命令驱动，「结束建设」由玩家显式确认触发，思考时间即武器 |
| 决策② 托管+微操混合 | C 相位行动槽是托管/微操的**唯一插入口**：每个守方单位行动槽开启时按其模式路由（手动=等玩家输入 / 自动=C10 即时决策），槽粒度切换、无特权通道 |
| MVS 确定性纪律 | 相位机为纯状态机+命令队列：同（存档态， 指令序列， F4 种子）→ 逐字节重放（X5 对拍/F5 存档回放地基） |

### 1.3 非目标（Non-goals）

- ❌ 单位速度数值、行动点（AP）经济规则 → C2（F2 只消费「该单位行动是否结束」的报告）。
- ❌ 敌军计划内容、波次构成与入场时刻表 → C8/C9（F2 只在 B 相位开口子）。
- ❌ 托管模式下的决策逻辑、Q5 半透明层可读性 → C10。
- ❌ 建造/部署指令校验 → C7（A 相位命令经 C7 校验后落 F1 mutation）。
- ❌ 粮饷数值、烽燧耐久数值 → C6/F3（F2 只定义 D 相位结算序与检查点）。
- ❌ 天气/时辰变量、夜战规则 → X6 Beta（「夜」在 MVP 只是关卡元数据透传，见 §3.2）。

### 1.4 关键裁定速览（TL;DR）

| # | 裁定 | 一句话 |
|---|---|---|
| A | 时间层级 | 战役(X1) → 夜(元数据) → **回合(F2 权威时钟)** → 四相位(F2 状态机) → 行动槽(C 相位内，速度序)；波次是 B 相位的入场事件流，不是时间层级 |
| B | 相位迁移 | 七态 FSM：`INIT→A→B→C→D→(A|END_WIN|END_LOSE)`，全部迁移显式枚举（§2.3），非法迁移硬拒绝 |
| C | 速度序排序键 | 主键 `speed` 降序（值归 C2/F3）；等速时**守方先动**（占位先于火力，平衡杠杆 F3 可调）；三键 unitId 字典序（确定性） |
| D | 行动槽生命周期 | 每单位每 C 相位**恰一个行动槽**：槽开启→单位行动至 C2 行动经济报告「耗尽/放弃」→槽关闭；留梯重试=下回合自身槽（C1 §2.4③ 的 F2 侧时序承诺） |
| E | 胜负检查点 | **唯一点**：D 相位第 ④ 步统一判定；C 相位内烽燧耐久归零→立即中止剩余行动序、带 `beaconDestroyed` 旗标进 D；「任意 3 座烽燧失守」解释为战役层计数归 X1（§5-E9） |
| F | 存档点 | 相位边界：关卡载入后（INIT→A）、每回合 D→A 迁移时自动存档；C 相位中段**拒绝存档**（行动槽中间态序列化不值得 MVP 背） |
| G | 事件边界 | 每相位发 `phase_enter/exit` 事件；P1/P4 订阅相位与行动槽事件做演出与 HUD，**禁止表现层驱动状态机**（与 F1 §3「表现禁反向驱动图论」同纪律） |

## 2. 机制

### 2.1 时间层级结构

```
战役（X1 关卡流转，3 关）
 └─ 夜 nightIndex（MVP 每关 1 夜；元数据透传，X6 Beta 挂变量）
     └─ 回合 turn = 1, 2, 3, ...（F2 权威时钟；F1 TerrainRuntime.turn 经 turn_started 事件镜像记账）
         └─ 相位 phase ∈ {A 建设, B 敌军, C 攻防结算, D 补给}
             └─ 行动槽 actionSlot（仅 C 相位；速度序，每单位每回合 1 槽）
```

- 「波次 wave」**不是时间层级**：它是 C9 时刻表的条目，在若干回合的 B 相位触发入场（`wave_entered` 事件）。一关 = 一夜至数夜的连续波次（概念稿 §4），具体波×回合映射归 C9 表。
- 回合计数从 1 起，在 D 相位结算完、迁移回 A 时 +1。F1 的 `TerrainRuntime.turn` 是镜像：F2 在 TURN_START 发 `turn_started{turn}` 事件，F1 订阅更新记账字段——**权威时钟只在 F2**（避免双写漂移）。

### 2.2 四相位职责与内部结算序（F2 裁定的执行顺序）

#### A 建设阶段（不限时，决策⑤）

```
A① 相位开启：发布部署区/建造预算快照（C7 消费），玩家指令窗口打开
A② 玩家任意顺序下达建造/修理/部署/撤收指令 → C7 校验 → F1 mutation（事件流）
A③ 玩家确认「开始敌军阶段」→ A→B 迁移
```

- 无墙钟、无步数上限——限制来自粮饷经济（C6）与部署区容量（F1），不由时间施压。
- MVP 战术单位（戍卒）在 A 相位**部署但不行动**：MP/行动槽全部属于 C 相位；A 相位只改静态布局。

#### B 敌军阶段（自动结算，瞬时呈现）

```
B① 波次入场：C9 按时刻表取出本回合入场条目 → 敌方单位经 F1 placeUnit 落出生端（F1 V2 校验区）
B② 可见性更新：MVP 全图可见（C12 简化裁定）；此处留 C12 Alpha 的可见性重算挂点
B③ AI 计划生成：调 C8.generatePlans()——意图脚本为本回合所有敌方单位产出计划；
   可达性评估在 ACTIVE ∧ BOTH 边图上运行（F1 §2.4.2 accessPolicy 消费契约，DEFENDER_ONLY 边对匈奴不存在）
B④ B→C 迁移（plans_ready 事件）
```

#### C 攻防结算阶段（速度序行动循环，本系统核心）

```
C① MP 重置：全部在场单位 MP 回满（C2 基准值），准备行动
C② 行动循环：按 §2.4 速度序逐单位开启行动槽：
     ├─ 敌方单位 → 一律 AUTO 路由：C8 按既定计划经 C1/C5 API 执行（与守方托管同轨）
     ├─ 守方单位·托管 → C10 即时决策并经同一套 API 执行
     └─ 守方单位·手动 → 等待玩家输入（无超时；输入经 P3→C1/C5 API），直至 C2 报告行动结束
C③ 迁移判定：全部行动槽耗尽 ∨ 烽燧被毁中断事件 → C→D（带/不带 beaconDestroyed 旗标）
```

- **世界冻结**：任一行动槽期间全状态只被该单位的指令改变（C1 §2.5 的前提），槽间状态对后续槽可见——先手优势的来源。
- 行动槽是托管/微操的**唯一插入口**：F2 不感知「托管是什么」，只按单位模式字段路由（§9 契约 1）。

#### D 补给阶段（自动结算，固定顺序——顺序本身是裁定）

```
D① 战场清扫：梯残骸清除（F1 E5：DESTROYED 记录退场，清场事件发 P1）
D② 粮饷收入结算（C6：屯田+缴获+补给线，数值归 C6/F3）
D③ 援军到岗（C6/C9 时刻表 → F1 placeUnit；落点满→顺延下回合，§5-E13）
D④ 胜负判定检查点（§2.5，唯一点）
D⑤ 波次计划推进（C9 cursor 前移）
D⑥ turn++ → 迁移判定（继续→A ／ 终局→END_WIN/END_LOSE；此边界自动存档，裁定 F）
```

### 2.3 相位状态机与合法迁移表

| 当前态 | 迁移 | 触发条件 | 副作用 |
|---|---|---|---|
| `INIT` | → A | 关卡载入且 F1 §8.4 校验通过 | 发 `battle_started`；自动存档点 S0 |
| A | → B | 玩家确认指令（唯一触发，无超时） | 锁定 A 相位指令队列，发 `build_phase_closed` |
| B | → C | `plans_ready`（C8 生成完毕） | 发 `combat_phase_started` |
| C | → D | 全部行动槽耗尽 **∨** `beacon_destroyed` 事件 | 旗标透传（`beaconDestroyed?`）；发 `combat_phase_ended` |
| D | → A | 检查点未触发终局 | turn+1；`turn_started`；**自动存档点 S1** |
| D | → END_WIN | 检查点判胜（§2.5） | 发 `battle_won` → 移交 X1（战利品/继承结算数据包） |
| D | → END_LOSE | 检查点判负（§2.5） | 发 `battle_lost{reason}` → 移交 X1 |

- 表外迁移一律拒绝并发 `illegal_transition` 错误事件（校验测试项，§8.2）。
- `INIT` 只出现一次；`END_*` 为终态，回滚/重开经 X1 重新载关。

### 2.4 速度序与行动槽（C 相位调度规则）

- **排序键（F2 裁定，数值归 C2/F3）**：
  1. 主键：`speed(u)` **降序**——快者先动（骑射手骚扰先手、冲车迟缓压阵的战棋直觉）；
  2. 次键（等速）：**守方优先**——设计理由：垛口/坡头抢位博弈中等速对决倾向守方，直接执行 P2「占位先于火力」，同时对冲攻方人数优势；此优先级做成 F3 表键 `tiePriority: 'DEFENDER_FIRST'`，平衡期可翻转；
  3. 三键：`unitId` 字典序升序——纯确定性，无玩法含义。
- **行动槽生命周期**：槽开启 → 单位行动（移动/攻击/技能/架梯…经 C1/C5 等 API）→ C2 行动经济报告「AP 耗尽 ∨ 显式放弃」→ 槽关闭。MVP 默认语义：**每单位每回合 1 槽**；AP 具体数值与「移动后可否攻击」归 C2（C1 OQ-2 同源），F2 的槽模型对「1 AP / 多 AP」都兼容。
- **留梯重试时序承诺**（C1 §2.4③ 的 F2 侧落点）：BLOCKED_TOP 单位保持 ON_CONNECTOR，其下个行动槽=**下回合 C 相位**自身速度序位置——等待以回合计，暴露承受打击（梯上 EXPOSED 修正归 C5），这就是「垛口堵击」的时间代价结构。
- **顺序快照**：速度序在 C① 重置后一次性计算并冻结为本回合行动序（中途单位死亡不重排，跳过其槽）——保证玩家可预读全场行动顺序（P4 HUD 时间轴，§6.1）。

### 2.5 胜负判定（检查点与条件归属）

| 判定 | 条件 | 归属 | 检查时点 |
|---|---|---|---|
| 守方败（单关） | 烽燧（帅帐）耐久 ≤ 0 | F1 beacon 耐久（值归 F3/C5 伤害） | C 相位内**立即中止**（带旗标进 D）＋ D④ 复核 |
| 守方败（战役层） | 「任意 3 座烽燧失守」 | **X1 战役账本**——MVP 单关烽燧唯一（F1 V4），此条件无法在关内成立，裁定为跨关累计计数（§5-E9，已报主理人转 X1） | X1 在 `battle_lost` 后结算 |
| 攻方败（MVP） | 波次耗尽 ∧ 场上无存活敌军 | C9 波次表（耗尽判定）＋ F1 snapshot（清场判定） | D④ |
| 攻方败（Alpha） | ＋士气崩溃 | C11 | D④ 同点位（MVP 不启用） |

- 「立即中止」语义：`beacon_destroyed` 事件到达时，**当前行动槽立即关闭**（在途指令执行完该条，不再开启后续槽），带旗标迁 D；D 相位仍走 D①-D③（清理与结算照常，保证世界一致），D④ 判负。玩家输得明白：烽燧倒下的瞬间战局就结束了，不再有「死后翻盘轮」。
- 胜利判定必须「波次耗尽**且**清场」两者同时成立：只耗尽不清场不允许提前胜利——最后一波残敌仍能爬上墙，这正是濒危险胜的收尾张力（P4）。

### 2.6 确定性纪律（与 C1 §2.6 同源，F2 侧承诺）

1. 相位机只由命令/事件驱动，无墙钟、无 `Math.random`（一切随机经 F4 种子）。
2. D 相位六步结算顺序固定（§2.2-D），结算内各系统调用顺序固定。
3. 行动序快照一次计算（§2.4），排序键全序无歧义。
4. 同（存档态， 指令序列， F4 种子）→ 事件流逐字节重放——F5 存档回放与 X5 对拍共同依赖。

## 3. 数据

> 引擎无关 TS。F2 持有战局时钟与调度状态，均为小体积纯数据（存档友好）。

### 3.1 战局调度状态（TurnState，F5 存档的 F2 部分）

```ts
interface TurnState {
  levelId: string;
  nightIndex: number;              // 元数据透传（X6 Beta 挂变量）
  turn: number;                    // 权威时钟，从 1 起
  phase: 'INIT'|'A'|'B'|'C'|'D'|'END_WIN'|'END_LOSE';
  flags: { beaconDestroyed?: boolean };
  actionOrder?: UnitId[];          // C 相位速度序快照（C 相位持久，出相位即清）
  slotCursor: number;              // 当前行动槽下标（存档用于相位边界校验，C 中段不可存档）——行动槽频次=每 C 相位 1 槽/单位（回合与 C 相位在 MVP 一对一，F2.2 语义以相位计）
  dbe: DPhaseLedger;               // D 相位记账（收入/援军顺延/波次 cursor，见 3.2）
}
```

### 3.2 D 相位记账（DPhaseLedger，跨系统钩子的持久凭据）

```ts
interface DPhaseLedger {
  incomeSettled: boolean;                    // C6 钩子完成标记
  pendingReinforcements: ReinforceEntry[];   // 落点满顺延的援军（下回合 D③ 优先重试）
  waveCursor: number;                        // C9 时刻表游标（权威在 C9 表，此处镜像）
  turnEndSnapshots: BattleEndReport[];       // 终局数据包（移交 X1）
}
```

### 3.3 相位与槽事件（供 P1/P4/C10/X5 订阅；事件流可重放）

| 事件 | 载荷 | 主要订阅方 |
|---|---|---|
| `turn_started` | `{turn, nightIndex}` | F1（镜像记账）、P4（回合横幅）、X5 |
| `phase_enter / phase_exit` | `{phase, turn}` | P1（演出切分）、P4（相位指示）、X5 |
| `action_slot_open / action_slot_close` | `{unitId, slotIndex, mode}` | P4（当前行动单位高亮/时间轴）、C10、P1（行动演出锚点） |
| `plans_ready` | `{plannedUnits: n}` | F2 内部（B→C 触发）、P4（敌方阶段结算提示） |
| `beacon_destroyed` | `{byUnitId?, atTurn}` | F2（C→D 中断）、P1（烽火熄灭演出）、P4 |
| `battle_won / battle_lost` | `{reason, stats}` | X1、P4（胜负横幅） |

### 3.4 读写边界（谁写谁读）

| 数据 | 写入方 | 读取方 |
|---|---|---|
| `turn / phase / slotCursor` | 仅 F2 | 全部（只读查询接口 TurnQuery，§6.2） |
| 行动序快照 | F2（C① 计算，读 C2 speed + F3 tiePriority） | P4 时间轴、C10、C8 |
| `pendingReinforcements` | F2（D③ 写）/ C6（提供时刻表） | F2 自身 |
| `beacon` 耐久 | C5（伤害）/ C3（修理，若有） | F2（判定）只读 |

## 4. 公式

> 统一格式：编号 ｜ 名称 ｜ 变量与单位 ｜ 表达式 ｜ 消费方。数值基准一律标「F3 表宿主」。

- `F2.1 ｜ 行动序排序键：ord(u) = (−speed(u), tier(u), unitId) 字典序升序 ｜ tier(守)=0, tier(攻)=1（F3 键 tiePriority，初值 DEFENDER_FIRST）｜ 消费方：C 相位循环/P4/C8/C10`
- `F2.2 ｜ 槽频次：slotsPerTurn(u) = 1（MVP 恒定；多行动模型为 C2 AP 经济，槽内消化）｜ 消费方：C2`
- `F2.3 ｜ C→D 触发：exitC ⇔ (∀u∈order: slotClosed(u)) ∨ beaconDestroyed ｜ 消费方：状态机`

## 5. 边缘情况

> 裁定者=本文；数值与内容归各属主。格式：编号｜场景｜裁定｜消费方。

### A. 相位与迁移

- **F2-E1｜A 相位零指令**：玩家不建不部署直接确认→合法，B 相位照常。空过是玩家权利（决策⑤不限时的另一面：不限时也不强迫）。
- **F2-E2｜B 相位波次入场与既有敌军并存**：C9 时刻表允许多波在场（前波未清后波入场）——B① 只负责「本回合条目落位」，不检查场上敌情；清场判定只在 D④（§2.5）。该设计使「佯攻接主攻」的连续压力成为时刻表问题而非状态机问题（归 C9 调表）。
- **F2-E3｜C 相位中段玩家关闭页面/断线**：网页游戏无服务器会话概念——页面刷新=读档，最近存档点为上回合 S1（裁定 F：C 中段不存档），损失本回合未确认的操作。UI 在 C 相位开启时提示「进行中的回合不会被保存」。
- **F2-E4｜非法迁移注入**：任何表外迁移（如从 B 直接调 `beginPhase('D')`）→ 拒绝 + `illegal_transition` 事件；fuzz 测试项（§8.2）。

### B. 行动槽与速度序

- **F2-E5｜行动序中单位死亡**：序快照不重排（§2.4）；轮到该单位时槽直接跳过（0 时长），`action_slot_open/close` 仍成对发出（载 `{skipped: true}`）——事件流配对性是 X5 重放的结构约束。
- **F2-E6｜留梯单位（ON_CONNECTOR）的行动槽**：下回合 C① MP 重置对梯上单位照常生效；其槽到来时若顶位仍满，经 C1 重试仍 BLOCKED_TOP → 槽即关闭（等待也是一次「行动决策：继续等」，期间持续 EXPOSED）。主动弃梯（C1-E4）在其槽内进行。
- **F2-E7｜全场戍卒阵亡但设施与烽燧尚存**：战局继续——床弩按 C4 相位自动运作（托管语义），玩家仍可微操设施目标（若 C4 允许手动锁定）；败北只认烽燧（§2.5）。该局面正是「濒危险胜」的最后一段。
- **F2-E8｜守方全部单位+全部设施被清空而烽燧尚存**：理论上仍进入下一回合（匈奴需先拆烽燧）——但波次若在此期间耗尽且清不了烽燧，D④ 判胜。荒局由 C9 波次表避免（最后波必带破燧能力，归 C9 验收），状态机不特殊处理。

### C. 胜负与跨文档

- **F2-E9｜「任意 3 座烽燧失守」× 单关烽燧唯一（跨文档张力，已裁定并上报）**：概念稿 §4 胜负条件写于 5 关/多烽燧设想期；定稿后 F1 V4 规定单关恰 1 座烽燧。**裁定**：单关败=帅帐破；「3 烽燧」解释为**战役账本条件**（累计失守 3 座=战役败，Alpha 多燧地图/战役地图启用），归属 X1 战役流程。MVP 3 关结构下该条件永不触发，X1 GDD 须显式标注其「休眠」状态防误实现。**已列 GW-P2-003 一致性评审输入。**
- **F2-E10｜烽燧在 A/B 相位被毁的可能**：不存在——一切伤害结算只发生于 C 相位（C5 消费槽事件），A/B 相位无攻击指令入口；C3 修理也只发生在 A。校验项：`beaconHP` 变更事件必须携带 `turn.phase='C'`，否则为非法（测试断言，§8.2）。
- **F2-E11｜胜负同回合双触发**（最后一波自爆与烽燧同回合归零）：D④ 检查点按「判负优先」——烽燧倒下即败，不因同回合清场而胜（悲壮感是支柱 P4，不是 bug）；顺序固定保证确定性。

### D. 存档与结算

- **F2-E12｜C 相位存档请求**：拒绝（裁定 F），返回最近 S1 存档点信息；P3 据此灰显存档按钮。理由：行动槽中间态（MP 消耗/半执行指令）序列化破坏「相位边界=一致快照」的简单性，MVP 不值得。
- **F2-E13｜D③ 援军落点满**：F1.placeUnit 拒绝 → 顺延（F2.7）；顺延条目在下回合 D③ **首位**重试，且重试失败可继续累积——长期无落点时援军堆积，由 C6/C9 表的落点配置保证不发生（关卡校验 V12 部署区可达已兜底）。
- **F2-E14｜END 终态后的事件**：终态不消费任何游戏指令；X1 接管前的 `battle_won/lost` 事件 payload（战利品/继承数据包）由 C6/X2 格式约定，F2 只透传快照引用。
