### 2.1 分层依赖图（文字化）

依赖方向自上而下读：上层消费下层；`→` 表示「被依赖」。

```
【外围层】X1 战役流程 ←(C9 波次+胜负判定+F2 相位)
          X2 建设继承 ←(C3 设施+C6 经济+F5 存档)
          X3 教学引导 ←(X1+全部机制定稿)
          X4 编辑器 ←(F1)   X5 模拟器 ←(F3+F4+C5)
          X6 天气 ←(C5 修正挂点)   X7 援军调度 ←(C12)

【表现层】P1 渲染 ←(F1 层级结构+核心层状态)

          P4 HUD ←(C5/C6/F2 状态)   P5 演出 ←(C5 事件流)

【核心层】F1 地形网格 → C1 寻路移动 → {C2 单位, C8 AI}
          F2 相位调度 → {C4 器械相位, C7 建设部署, C9 波次, C10 托管微操, X1}
          C2+C3 → {C4, C5 攻防结算}
          C2 → C9 波次编排 → C8 匈奴AI
```

## 3. Phase 2 逐系统 GDD 撰写顺序建议

> 原则：**依赖排序为主轴，风险优先做插队**——最不确定的系统最先写，给实现侧留迭代时间。

| 序 | GDD | 理由（一句话） |
|---|---|---|
| 1 | **F1 立体地形与网格系统** | 用户改判「直接立体战棋」的最大不确定性落点＋全局地基；网格/层级/连接器/占位模型不定，下游全部空转 |
| 2 | **C1 寻路与移动系统** | 直接依赖 F1，技术不确定性第二；A*/flow field 选型与「云梯=动态连接器」模型在此定 |
| 3 | **F2 回合与相位调度系统** | 游戏主干状态机；器械相位、托管微操、波次接口全挂在四相位上，契约宜早定 |
| 4 | **C2 单位系统 ∥ C3 防御设施系统**（可两份并行） | 定义全部兵种/设施数据契约；**督队 MVP 简化职责在此裁定**（士气延后的张力，见 §6.2） |
| 5 | **C4 器械相位 ∥ C5 攻防结算**（弱依赖可并行） | P2 支柱「高度即力量」的数学落点：高度修正/穿透列/目标选择公式依赖序 4 的数据契约 |
| 6 | **C8 匈奴 AI 系统** | 概念稿点名「AI 弱则崩」为最大设计风险，风险优先原则要求前半程定意图脚本＋评分框架，留足实现迭代期 |
| 7 | **C6 粮饷经济 ∥ C7 建设部署**（并行） | 相对确定性高，依赖相位契约即可写 |
| 8 | **C9 波次编排 ∥ C10 托管微操**（并行） | 关卡节奏＋操作手感的最后拼图，直接服务「濒危险胜」验证判据 |
| 9 | **X2 建设继承 ＋ F5 存档 ＋ X1 战役流程** | 外围收口，需前置数据结构（设施/经济/关卡）稳定后再写 |

**跨职能对齐点（建议经主理人安排）**：

## 4. 各系统与「共享数值层」的关系

**原则**：克制表、兵种属性、公式系数、波次构成全部落引擎无关的 JSON/TS 模块（决策⑥），A 案为数值基准版；B 案已确认克制表/兵种数值直接复用，未来 B 案复活时**只改消费节奏（回合制相位 → 实时冷却/流速），不改表结构**。

| 数值角色 | 系统 | 说明 |
|---|---|---|
| **数值载体**（拥有表，改动需过平衡评审） | C2 兵种属性表、C3 设施表、C5 命中/伤害/高度修正系数、C6 经济参数、C9 波次构成表、C11 士气阈值（Alpha）、X6 天气修正（Beta）、**克制表（两案共享根表）** | F3 是这些表的唯一宿主；GDD 中「数据」一节直接引用 F3 表结构 |
| **数值消费方**（只读，可调权重不改表义） | C1 移动消耗、C4 装填/架设时长、C8 AI 评分权重、C10 托管决策权重 | 消费方 GDD 需声明读哪些表字段，禁止私藏数值 |
| **数值无关**（纯结构/表现） | F1/F2（结构）、F4/F5（基建）、P1-P6（表现层只读状态）、X1/X3（流程）、X4/X5（工具） | — |

**B 案复活挂载点**（归档稿 §6 已确认）：根表＝克制表＋兵种属性＋公式系数三件套；B 案新增的仅是「实时化消费参数」（如礌石冷却 20 秒、预警提前量），作为表的附加列/旁表挂载，不动根表。

## 5. 「直接立体战棋」专项风险评估（决策①改判）

> 用户改判：不走 B→A 剖面过渡，MVP 直接上多层立体战棋。缓解措施已锁定：走廊式关卡＋编辑器推 Alpha＋意图脚本 AI。本节评估三大风险点（3D 网格/寻路/遮挡）在走廊式约束下的**最小可行方案**。

### 5.1 走廊式关卡的结构骨架

```
高度层 2   ┌─────────┐                    烽燧顶（帅帐/视野制高点）
高度层 1   │ 垛口 马道 垛口 │  ←── 守军主防线（床弩/礌石/戍卒）
连接器          ▲坡道      ▲梯道（匈奴云梯=动态连接器）
高度层 0  ──────────────────────  地面（匈奴集结/冲锋/冲车道）
           ├──── 单段城墙走廊 ────┤
规模建议：横向 12-20 列 × 纵深 2-4 格 × 高度 0-2 层，全图格子总量 ≈ 200-400
```

### 5.2 三大风险点的最小可行方案（MVS）

| 风险点 | 最小可行方案 | 降维效果 |
|---|---|---|
| **3D 网格** | 不做自由 3D/体素。用**分层 2D 网格（2.5D heightmap grid）**：每格 `(x, z)` 持有高度标签 `h∈{0 地面, 1 墙顶/马道, 2 烽燧顶}` 与类型 `{墙/垛口/马道/坡道/地面/门洞}`；跨层只经**显式连接器**（坡道/楼梯），寻路图＝各层 2D 图在连接器处并边 | 3D 问题 → 2D 图论问题；格子数百级，数据手写可维护 |
| **寻路** | 分层图上跑 **A\***（或按目标点预计算 flow field，匈奴单位跟流场）；**云梯建模为「动态连接器」**——架设后把地面格与墙顶格连边、被毁则断边，与坡道共用同一套图论模型；回合制离散移动＋每格容量检查，天然无需实时避障/群体模拟 | 消灭实时 crowd simulation；「爬城」与「走坡道」统一为一个模型 |
| **遮挡** | 相机规避＋切层渲染：高位 Ortho 鸟瞰为主机位（B 案对比表既定方向）；聚焦某高度层时更高层墙体半透明/轮廓化；走廊纵深浅、守方视角从墙内侧看，遮挡场景天然低频。MVP 只做「选中高亮描边＋相机地面档/墙顶档两档位＋上层半透明」，不做逐像素遮挡剔除 | 渲染表现问题，非引擎难题 |

### 5.3 结论：**有条件可行**

成立需同时满足四个条件：
1. **严守走廊式关卡**——单段城墙＋有限连接器，不做多段迂回/自由爬墙；
2. **分层 2D 网格＋显式连接器建模**，不做真 3D 寻路；
3. **云梯=动态连接器**的统一图论模型被 C1 GDD 正式采纳；
4. **相机用固定档位＋切层渲染**，不做自由镜头。

四条全部满足时，三大风险点均降维为「2D 图论＋渲染表现」，在 Three.js＋6 周内可行（F1/C1 仍是全项目最大工程项，须按 §3 序 1/2 先行）；**任何一条被打破（尤其关卡走廊化放松），风险即回升为「数月级产能陷阱」**（概念稿 §10 原判）。

### 5.4 残余风险（需在后续 GDD 中裁定）
